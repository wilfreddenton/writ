# GUI library for writ: evaluation & pick

## Verdict
The single best choice for writ is the **Linebender primitive stack (winit + wgpu + Vello + Parley, with Taffy optional)** — it is the only candidate that scores 5/5 on all three existential axes (editor-suitability, text-fidelity, maintenance) and directly kills both of writ's gpui pain points. The runner-up is **Xilem/Masonry**, which wraps that same Parley+Vello stack in a real widget/paint framework and is the better pick only if writ wants an app shell handed to it rather than hand-building one.

## Why the winner
Writ is being driven off gpui by two things: (1) a frozen, effectively unpublishable crate, and (2) a hand-rolled `is_word_char` line-breaking heuristic that doesn't match browsers. The Linebender stack answers both cleanly and *verifiably*. On publishing: Parley 0.11.0 and Vello 0.9.0 workspace versions **exactly match** the latest crates.io releases, both repos are very active (Parley 44 commits/90d, Vello 110/90d, HEADs late June 2026), and everything is Apache-2.0 OR MIT — so `cargo publish` and `cargo install` work again, which is the entire reason for the migration. On text: Parley drives genuine `icu_segmenter` UAX-14/29 line/word/grapheme breaking with HarfRust (HarfBuzz-class) shaping and Skrifa/Fontique, and ships a tested `CHROMIUM_LINE_BREAK_OVERRIDE` table mirroring Blink that writ can opt into with one `set_line_break_override` call — obsoleting the patched heuristic outright. Critically for writ's *custom-editor* nature, this is a primitive layer, not a widget set: you get a `parley::Layout` you draw glyph-by-glyph into a Vello `Scene` (`scene.draw_glyphs` over `GlyphRun`s), full hit-testing (`Cluster::from_point`/`from_byte_index`/`visual_offset`), cursor/selection geometry, per-range styling via `RangedBuilder`, inline boxes, and a ~982-LoC working `vello_editor` example (IME preedit, clipboard, pointer selection, AccessKit) to fork. That is exactly the surface writ needs for hidden markdown markers, bespoke cursor/selection, per-line ghost-diff lines, and hover popovers.

The winner's biggest honest risk is that **it is not a framework at all**: there is no gpui-like element+Context/entity/reactive model, no windowing, no event loop, no widget tree. Writ must hand-build the whole app shell — winit loop, wgpu+Vello lifecycle, input/IME/clipboard routing, scrolling, gutter, popover compositing — and swallow periodic 0.x breaking churn (recent commits rename public API and the example even lags the workspace vello version). This is a re-architecture, not a mechanical port (migration 2/5). But that cost buys total control, which is what a bespoke editor surface wants anyway, and it is bounded and one-time — unlike the publishing dead-end that gpui and floem impose.

## Runner-up & when it'd win instead
Xilem/Masonry (4.38) is the same winning ingredients — Parley UAX-14 shaping into a Vello scene — but served inside a real retained framework: Masonry's `Widget` trait gives you `paint(&mut Painter)`, `on_text_event` (IME + hit-testing), `measure`/`layout`, a `Canvas` widget, and a `custom_widget.rs` example, and its `render_text` iterates Parley `GlyphRun`s for full per-glyph control. It also ships `vello_cpu`, a software fallback that partially de-risks Vello's GPU-compute maturity on Asahi/ARM. **Xilem wins instead if** writ decides it does not want to own the winit/wgpu/IME/scroll plumbing and would rather implement one bespoke `Widget` on `parley::Layout` inside an existing app+event framework with AccessKit already wired. The reason it drops to runner-up is exactly writ's pain point #1: crates.io was last updated 2025-10-29 (~8-month lag) while the repo pins parley 0.8/vello 0.8 vs 0.11/0.9 published — a *softer* echo of the gpui trap. It still uses real semver and is publishable (better than gpui or floem), but the winner has zero registry lag, which for writ is decisive.

## Migration sketch
Building writ's editor surface on the Linebender stack looks like:
- **App shell (new):** a winit event loop + wgpu device/surface + Vello `Renderer`, driving a redraw. This is the bulk of the from-scratch work; the `vello_editor` example is a direct scaffold.
- **Document model:** keep writ's rope/buffer. Do **not** lean on Parley's `PlainEditor` (single-brush plain text) — writ's live inline markdown (hidden markers) + tree-sitter styling needs you to drive `RangedBuilder`/`Layout` directly and re-apply styles per edit. You can still crib editing semantics (`delete_word`, `move_up/down`, `selection_geometry`, `cursor_geometry`) from the PlainEditor source.
- **Per-line rendering:** for each visible line, build a Parley `Layout`, push tree-sitter color/style ranges + markdown-marker hide/show ranges via `push`/`push_default`, then draw glyph-by-glyph into the Vello `Scene`. Cursor, selection rects, and ghost-diff lines are your own `scene.fill`/`stroke` calls; hit-testing uses `Cluster::from_point`.
- **Line-breaking:** call `set_line_break_override(CHROMIUM_LINE_BREAK_OVERRIDE)` to match browsers (default is plain UAX-14). This replaces the patched `is_word_char` code entirely.

Rough effort: **high** — several weeks, dominated by the shell and input/IME/clipboard routing, not the text rendering (which the example already demonstrates). Migrating from gpui's element+Context model is a re-architecture, not a port.

Top risks:
1. **App-shell surface area** — IME, clipboard, scroll, focus, and popover compositing are all yours to build and get right (the example covers IME/clipboard as a starting point).
2. **0.x API churn across two repos** — Parley and Vello version-drift (the example itself lags the workspace); expect periodic breaking upgrades and pin deliberately.
3. **Vello GPU maturity on Asahi/ARM** — compute-shader-heavy; mitigate by keeping `vello_cpu`/`vello_hybrid` as a fallback path from day one, since writ runs on Asahi Linux.

## Notes
- **The Parley + Vello stack recurs across the entire top of the field** — it is the winner directly, is what Xilem wraps, what blitz exposes under its DOM, and what floem adopted on HEAD. The consistent signal is: writ's real target is *Parley for text + Vello for GPU*, and the only question is how much framework to bolt on top. The pure-primitive layer wins because it adds zero publishing lag and maximal control.
- **The gpui trap is not unique to gpui.** floem is arguably worse — crates.io frozen at 0.2.0 since 2024-11 (two tags ever), 297 unreleased commits, and non-optional git deps (a forked winit, five understory crates, and a *default* vger renderer that is itself a git dep) make even a default build unpublishable — and the Parley text stack writ wants exists *only* on that unpublishable HEAD. makepad shows the same pattern (1.0.0 published vs 2.0.0 repo). Any candidate requiring a git pin fails writ's #1 requirement; that alone sinks floem and makepad despite floem having the best editor primitives (Lapce lineage: xable buffer, phantom-text mapping onto hidden markers/ghost lines).
- **Immediate vs retained fit:** egui (immediate mode) and iced (Elm/retained) are both architecturally distant from gpui and, more importantly, cap the editor. egui keeps writ's *exact* line-break problem (hand-rolled heuristic, no `unicode-linebreak` dep) despite great publishing; iced has real UAX-14 (cosmic-text) and excellent publishing but tops out at grapheme/span granularity with **no raw glyph-run/paint-glyph access** — a real step down for a per-glyph custom editor.
- **blitz is the right text stack in the wrong shape:** it has browser-grade Stylo+Parley on wgpu/Vello and is genuinely published, but it is an HTML/CSS/DOM engine whose only bespoke-editor path bypasses its entire reason to exist. It's a strong argument for adopting Parley + anyrender_vello directly rather than fighting a DOM — which is exactly what the winner is.
- **License gate:** all seven pass (no GPL/commercial). blitz's transitive Stylo is MPL-2.0 (file-level weak copyleft, acceptable); everything else is MIT or Apache/MIT.
